# 随机题库、排盘与图片导出

## 数据入口

`data/characters.json` 是名字及查询别名的权威表。`data/clues.json` 是当前游戏的提示库，关联同一个 `characterId`，不重复保存英文或片假名答案。格式定义见 `schemas/clues.schema.json`。

`data/roster.json` 是经过人工审校的官方名单快照，记录145位主要马娘、17位剧情辅助马娘、36位已审校漫画原创角色及工作人员排除项。`npm run audit:roster`只读联网比较官方名簿变化；离线`check:data`检查普通题组是否覆盖整个词典。具体范围与逐类来源见[题库扩充与来源核对](题库扩充与来源核对.md)。

每个角色记录包含 `categories` 和多条 `clues`；每条提示有稳定 `id`、适用题组、`dimension`、`text` 三语正文及 `sources`。新记录还含事实键 `factKey` 和核实日期 `verifiedAt`；`horse-life`近况强制包含`asOf`且不晚于核实日期，正文也应注明资料月份／年份。维度新增`music`和`official-program`，分别对应经核实的独唱曲目与官方企划。不同题组可以共用角色，但抽取的提示范围由每条提示的 `categories` 限定。入门偏重完整人物特征，进阶提高比赛记录等线索的抽取权重。

2026-10-16核对后收录198位角色、1009条三语提示记录。入门和进阶候选角色各198位，各有869条可用提示；二つ名候选 85 位，芦毛灰姑娘候选 51 位、160 条剧情提示。同一条提示可供多个题组使用，因此各题组提示数相加不等于记录总数。

普通题每个适用角色至少有两条提示；剧情题每位至少两条，按已核实的不同事实编写；同场比赛的不同情节可以分别使用，不能只改写同一句话。二つ名是角色固定称号，不为了增加变化而编造称号；原始表中两种称号并存时保留两者。二つ名中文、英文为项目译文，不宣称官方译名。

玩家本机只记住每位角色最近使用的提示 ID，下次遇见该角色且还有其他可用提示时避开上一条；这不是访客身份标识。禁止只用「很努力」「擅长跑步」等泛化描述。新增提示应含可锁定角色的年份与比赛、明确关系、独有称号或具体剧情等证据，并由维护者检查语义唯一性。程序只能检测重复文字映射到不同角色，不能替代事实审校。

`data/cinderella-roster.json` 保存51位剧情候选及暂缓项；`docs/evidence/cinderella-scenes.json` 将160条提示逐一关联到动画话数、漫画章段或作品人物介绍。两份审校资料会在离线校验时与运行题库比对，参见[灰姑娘扩充核对](灰姑娘题库扩充与核对.md)。

原有八套固定关卡保留在 `data/levels/`，作为历史资料和测试夹具，不再出现在开始页，也不参与当前运行时抽题。不要通过修改历史棋盘来新增随机提示。

## 生成流程

`src/generator.js` 为无 DOM 的确定性生成器，`generator-worker.js` 在浏览器 Web Worker 中执行。

1. 根据题组筛选角色，使用 32 位种子与固定 PRNG 洗牌，不放回抽样。小棋盘取 12 位、大棋盘取 20 位。
2. 放置首词；建立已用格子的字母与横纵占用信息。其余词仅枚举与相同字母交叉的位置。
3. 检查字母一致、方向不能重叠、词首尾留白、非交叉格两侧不相邻。每个新词必须交叉已放置的词，保持连通。
4. 按盘面面积、长宽差、交叉数量、方向平衡与小幅随机扰动打分。横竖各限制为 6 或 10 题，边长分别不超过 30 或 40 格。
5. 当前布局无法放完全部抽中角色时换顺序重试，仍失败则重新抽角色。总计最多 160 轮、每轮 3 次布局尝试；不会返回残缺或不连通棋盘。
6. 裁去外围黑格，按从上到下、从左到右统一编号；为每位角色抽提示，再调用 `validateLevel` 检查全部语义约束。

这是一种受限随机重启搜索，候选启发式参考 [Stanford 的填字与约束满足研究](https://web.stanford.edu/~jduchi/projects/crossword_writeup.pdf)。本项目处理的是从名字生成自由形状棋盘，并非照搬固定网格求解算法；抽样也不是对全部合法盘面进行均匀采样。同一题库、算法版本和种子可复现盘面；提示还受本机近期记录影响。

手机默认小棋盘，电脑默认大棋盘，玩家可覆盖默认值。尺寸指题数，不是固定的格子边长；长英文名仍需更多列。界面保持可读格子宽度，支持横向拖动和缩放，不强行缩小整张棋盘来塞入手机宽度。

## 生成速度验证

运行 `npm run benchmark`；可指定 `-- --trials=50 --output=docs/generator-benchmark.json`。报告覆盖四题组 × 两文字 × 两尺寸，记录平均、P95、最大耗时、失败次数和边长。

随仓库提交的实测报告共 800 次生成，全部成功；分组平均约 3–20ms。这是开发机 Node.js 的算法加语义校验耗时，不包含网络、Worker 启动和 DOM 渲染，也不能代表手机速度。

开始按钮立即进入忙碌状态；400ms 后仍未完成才显示不定进度条和排盘说明，10 秒后结束本次尝试并保留旧局。游戏计时在新棋盘生成完、创建会话时才开始。修改生成器后应重跑测试和基准，不设置容易受机器速度影响的硬性耗时单测。

## 图片与投稿

`src/export.js` 使用 Canvas 本地生成 PNG，无截图服务或第三方二维码请求。图中包含完整棋盘、当前界面语言的全部横纵提示、网址及二维码。公开网址常量为 `https://umamusume-crossword.pages.dev/`；换域名时应同步修改及验证。

游戏中可下载空白或当前填写盘面；成功与提前结束后可下载答案版。时间与结束状态由玩家勾选加入，默认不加入；导出不会暂停游戏。图片可保存和打印，但不是固定纸张尺寸的分页 PDF。

二维码使用 [Project Nayuki](https://www.nayuki.io/page/qr-code-generator-library) 的 MIT 许可编码器，离线随站点分发；来源和许可证保留于 `src/vendor/qrcodegen.js`。更新该库后需重新独立解码验证 URL，不只检查图案外观。

主界面和结束弹窗均有 GitHub Issue 与 `iaparameter@gmail.com` 投稿入口；Issue 表单要求角色、提示和来源。新增投稿需人工核实，不能将用户提交直接写入公开题库。
